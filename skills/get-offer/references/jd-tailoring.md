# 按 JD 定制

把岗位要求和已有证据逐项对齐，再选择经历、顺序和表达。JD 是岗位资料，不能直接成为候选人的技能清单。[真实性规则](truthfulness.md)同样适用。

## 读取与范围

- 读取 JD 原文或确实可访问的岗位链接、经历库与通用简历，记录公司、岗位、来源和材料日期。
- 链接打不开就请用户贴正文，不假装读过。招聘时效、地点或申请资格需要当前信息时，只以提供的 JD 或核实过的官方来源为准。
- JD 缺失时可以做通用定位，不声称完成特定岗位匹配；简历缺失时先分析 JD，再只问最关键的经历信息。

## 拆要求

区分以下内容，不把所有关键词等权处理：

1. 明确的硬条件：如毕业窗口、地点、工作许可、语言或必要资质。
2. 岗位要解决的任务和期待产物。
3. 必需技能与经历证据。
4. 加分项及可迁移经验。

JD 没写清必需程度时标为待核实。涉及资格规则或行业制度的判断，限定到对应地区、时间和官方材料，不能凭常识作保证。

用[岗位任务与证据](role-evidence.md)把要求落到具体产物和判断过程，区分不同岗位对同一经历的侧重点；以当前 JD 为准，参考表不替代招聘方要求。

## 匹配报告

使用[匹配报告模板](../assets/jd-report-template.md)。每条要求回指经历和事实 ID：

| 分类 | 含义 |
|---|---|
| 有直接证据 | 经历库有确认的动作、产物或结果 |
| 有可迁移证据 | 能力相关但场景不同，需要说清可迁移之处和限制 |
| 待核实 | 当前材料没有说清，不能视为具备或缺失 |
| 明确差距 | 用户明确表示不具备，或已有事实与硬条件冲突 |

先给带依据的总体判断，再列主要优势、关键缺口与可执行补救。缺少材料时保留判断，不给精确的“匹配率”、录用概率或 ATS 通过保证。

用户要求打分时，可以先约定一个透明的准备度量表，逐项展示依据和未知项；分数仅帮助比较准备重点，不代表招聘方标准。明确硬条件不满足时直接说明，不用总分掩盖它。

## 改简历

1. 从经历库挑与本岗位任务最相关、证据最强的经历。
2. 按[经历组织规则](resume-structure.md)决定保留原结构还是局部重组；重排经历与要点，把直接证据放前面，动作与对应结果就近出现。
3. 使用 JD 的专业表达描述同一事实。原意不相同的词不替换，参与不改成主导，用过不改成精通。
4. 精简无关信息；保留能证明迁移能力的课程、社团和个人项目，不因没有同名岗位经历就全删。
5. 每条关键改写能回指确认事实。新增建议与尚未完成的练习单列。

## 缺口怎么补

按投递或面试时间选择一个最有价值的动作，按[补练任务规则](role-evidence.md)给出可立即使用的材料、预计投入、具体产物和验收方法。临近面试先整理已有证据，不承诺几小时补齐陌生技能。用户完成后检查实际成果和独立解释，再决定能支持多大范围的能力描述。

硬条件无法短期改变时，说明真实限制，给相邻岗位或另一个投递方向的判断方法，避免承诺“包装后就能过”。

## 交付与版本

- 保存 JD 原文和匹配报告到个人 `jd/`；岗位草稿及正式源稿均按[交付规则的命名与版本](delivery.md#格式与版本)保存到 `resumes/`，保留通用版及其他公司的版本。
- 整份目标简历可投递时，按[交付规则](delivery.md)导出本轮目标版。
- 修改说明列“选了什么、删了什么、换了什么表达、依据哪些事实”。
- 更新或覆盖用户指定的旧版时保留可恢复副本，不把岗位要求回写成个人已确认经历。
- 更新任务记录中的本岗位阶段、实际版本、待解决问题和下一步，以及材料入口的当前文件。
- 聊天用两三处实际改写说明取舍，让用户看见变化；完整匹配表和内部事实引用放报告。

最后一句可衔接到面试准备：围绕这一版简历和 JD，挑最可能被深问的证据点继续准备。
