# 简历撰写与修改

## 从当前材料开始

先读取已存在的经历库及用户本次材料。已有目标、毕业时间或经历不重复问；有现成简历就先诊断，不要求从零重填。[真实性规则](truthfulness.md)用于处理数字、职责和来源。

首次写简历、材料零散或不知道要提供什么时，读取[首次信息收集与素材盘点](first-resume-intake.md)，分轮了解背景、找素材，再选一段展开。已有足够写句的经历时直接改写，不要求先走完信息收集。缺少目标方向不妨碍先整理通用素材；投递节点只在影响本轮取舍时追问。

不默认索取身份证、详细住址、家庭和婚姻信息。联系方式由用户按投递用途提供，演练使用虚构标记的资料。

## 一次挖一段经历

按[经历库模板](../assets/profile-template.md)建立 E001 等稳定编号，每条可复用事实使用 E001-F01 等编号。每轮最多三个问题，优先问缺失且会改变表述的部分，并说明用途。

1. 背景和目标：要解决谁的什么问题，原来怎样处理。
2. 个人动作：你负责哪部分，用什么方法或工具，和其他人怎样分工。
3. 难点和判断：哪里卡住，为什么选这个做法，比较过什么选项。
4. 结果：交付、采纳、使用反馈或有来源的数值，区分团队结果与个人贡献。
5. 复盘：如果重做会改变什么，依据是什么。

不需要一轮问完五段。用户只有“参加过一个活动”时，可以先问负责什么、做了哪个具体动作、留下了什么产物。对用户真实行为的追问，比替他填一段完整项目更有用。

已知“个人做了什么、交付了什么”时，先给一条能用的简历句，再追问最影响这条句子的缺口。用户补充后立即合并成新句，并说明是否已可用。只有任务和动作、尚无结果时也可准确写出动作，不强行等待量化成果。已有准确稿且仅剩丰富细节时结束本轮，赶投递时优先完成整份可用稿。

## 形成可追溯的经历库

- 已明确陈述的事实记录原话或材料定位与确认状态；不能访问的文件注明未读取。
- 推算数字保存输入、计算过程和用户确认；没确认的留在待确认区。
- 用户回答与旧稿冲突时保留两处来源，只问最关键的冲突，不擅自选对简历更有利的一版。
- 用户要直接改现成简历且授权保存时，可将确认信息整理入库后继续，不重复申请相同的修改许可。

## 简历诊断顺序

先给三项以内最影响理解或投递的具体问题，再改写：

| 层次 | 检查什么 | 怎么改 |
|---|---|---|
| 方向 | 目标岗位与主要证据是否对应 | 重排相关经历，明确求职方向 |
| 事实 | 个人贡献、技能程度、数字口径是否可解释 | 标出冲突和待确认，不擅自补齐 |
| 表达 | 是否只有“负责、参与、协助”，缺动作与产物 | 写明动作、方法和可验证结果 |
| 阅读 | 信息层级、重复、篇幅与格式 | 优先保留相关证据，压缩弱内容 |

反馈引用原句，给出改后句，并说明依据或还缺什么。材料存在的缺口与用户能力不足分开，不因一段写得简略就给人下判断。

## 写通用版

使用[简历模板](../assets/resume-template.md)，按目标岗位选择栏目。教育、经历、项目、技能等栏目按证据需要取舍，空栏目删除。默认尽量紧凑，真实经历较多时由用户需要决定页数。

需要判断一段经历对岗位的价值时，读取[岗位任务与证据](role-evidence.md)，以任务、个人产物和决策证据选择重点；不把活动名称或岗位关键词当作能力证明。

经历要点用“背景或任务 + 个人动作与方法 + 可验证结果”浓缩表达。难点、决策和复盘的完整版本保留在经历库，供面试展开。结果不足时可以交付清楚的动作与产物，不强行写增长或节省比例。

技能按实际用到的程度写，避免从 JD 直接复制“精通”。岗位名、日期、奖项与工具不因措辞优化发生事实变化。

## 交付

1. 通用版简历，注明可直接使用或待确认草稿。
2. 三项以内主要修改及理由，必要时列原句与新句。
3. 另列仍待确认的事实及对应经历 ID，未确认内容不混进最终简历。
4. 有文件能力且用户允许保存时，写到个人目录并读回；已有同名稿默认留版本。

完成整份可投递简历时，按[交付规则](delivery.md)默认生成并检查 PDF 和可编辑 DOCX。用户只要草稿、局部改句、特定格式或不保存时，不扩大交付。保存后更新任务记录中的实际版本与下一步。

有明确下一步时只提示一句；当前任务已完成且没有待办时可以直接结束。
