# 简历初稿与投递稿交付

用户要简历时，按稿件阶段直接给对应文件；用户指定格式、只要聊天文字或不保存时，以本轮要求为准。

## 何时导出与交哪一版

- **完整初稿**依据已确认的经历写成后，当轮保存源稿，生成、核验并交付 PDF，在回复和材料入口标明“初稿”；联系方式等个人字段可按用户意愿留空。带空位的[待补稿](resume-builder.md#材料撑不起这个标准时)也导出 PDF，标明“待补草稿”。
- **投递稿**默认交 PDF 和可编辑 DOCX。用户要最终文件、确认回写后重新导出或赶投递时，直接处理当前版本。
- **素材收集和局部改句**只更新工作稿，用户明确要某个片段的文件时才导出。
- 目标岗位已明确时交本轮岗位版，通用源稿留作复用；未定岗位时交通用版。

## 出稿条件

- 身份、教育或相关背景及核心经历足以形成完整简历。联系渠道由用户提供，也可明确选择不公开；用户选择自己填写时直接交初稿 PDF，投递前再补。
- 可选成绩、照片、数字和弱相关栏目可以省略。删去受冲突影响的主张后仍能准确呈现就继续交付；仍有关键冲突的部分不能标成可直接投递。
- 正文只放求职内容，来源编号、内部标签、待确认问题、修改说明和模板指令放在单独记录里。待补稿例外：`[待确认：……]` 空位保留并醒目显示（墨蓝模板用 `.pending`），页头加一行稿件提示，例如“待补草稿，空位补齐前勿投递”（源稿里写成 `>` 开头的一行，模板用 `.draft-note`）；投递稿里两样都不能有。示范材料始终保留虚构身份，不用于实际投递。

## 格式与版本

- 每种被请求的格式各自选工具、各自核验：一种成功后仍要处理另一种，只要一种时不额外导出。宿主只有 PDF 能力时，也检查本机有没有可用的 DOCX 工具。不为此安装大型依赖、索取密钥或上传到外部转换站。

  | 格式 | 首选 | 首选不可用时 |
  |---|---|---|
  | PDF | 运行 [scripts/build_resume_pdf.py](../scripts/build_resume_pdf.py)，只需 Python 3.8+ 标准库和本机的 Chrome、Edge 或 Chromium | 宿主现有的文档或 PDF 能力；或[手工填模板](resume-style.md#手工填模板)后用无头浏览器打印，例如 `chrome --headless --no-pdf-header-footer --print-to-pdf=<目标>.pdf <页面>.html`。能跑 Python 时再用脚本的 `--check-pdf` 核验 |
  | 可编辑DOCX | 宿主现有文档生成能力 | 本机已有的 DOCX 工具；macOS 可用 `textutil -convert docx`，但产物没有 `word/styles.xml`，也未设 A4 和中文 `eastAsia` 字体，渲染时中文可能不可见。补写样式、`w:eastAsia` 字体和 A4 的 `sectPr` 后重新渲染核对，仍有样式缺失就如实说明降级 |

- **PDF 脚本。**源稿按[简历模板](../assets/resume-template.md)写，写法以脚本 `--help` 为准。运行 `python3 <技能目录>/scripts/build_resume_pdf.py <源稿>.md`，在源稿旁生成同名 PDF 并自动核验。初稿和待补稿不加参数；真实投递稿加 `--final`，空位、草稿或演练标记、内部标签都算问题；演练材料的最终版加 `--final --sample`，其余照查，但“---”之后的虚构标记必须保留并写明是演练或虚构材料，通过后仍是演练稿，不称为真实投递稿。英文简历脚本会自动按英文处理，也可加 `--lang en`。用户允许多页时加 `--max-pages N`。别的工具生成的 PDF 用 `--check-pdf <成品>.pdf --source <源稿>.md` 核验，手工填好的页面用 `--html <页面>.html --source <源稿>.md` 打印并核验。
  - 退出码 0：生成并通过检查，可能附提醒；“页面可能没写满”按下文核验第 3 步处理。
  - 退出码 1：有问题，逐条写了是什么、在哪、怎么修。这时不写正式文件，打印出的 PDF 另存到系统临时目录、文件名带“未通过”，只供查看；正式位置原有的旧文件不覆盖，结果里会提醒它和当前源稿不一定一致。修好后重跑。
  - 退出码 2：没法运行，例如参数错、找不到浏览器、源稿结构不认识（附行号）。结构问题按提示改源稿；没有 Python 或浏览器时用上表的备选。
- **页数。**国内校招默认 A4、简洁单栏、一页基本写满；英文和海外投递按明确的岗位要求选纸张，不把所有英文简历都设为 Letter。用户指定的纸张和页数优先。内容多时先收紧间距：脚本超页时自动改用紧凑间距重排，字号不变，输出的“间距”一行写明用了哪一档。仍排不下就删重复和弱相关内容，不缩字号、不裁切、不隐藏正文、不整体缩印。用户没限定页数、一页确实无法保持可读时，可以自然分成多页并说明取舍（脚本加 `--max-pages N`），每一页都要看；用户限定一页就继续精简，不静默增页。
- 源稿与交付的 PDF、DOCX 是同一内容版本，源稿保留以便后续修改。正常导出保持视觉层级一致；textutil 等降级路径没保留样式或纸张时说明实际差异，修复后重新渲染核对，未经核验的降级文件不称为同样式成品。
- 导出中的临时文件（页面截图、提取的正文、`--save-html` 另存的页面、构建脚本、失败稿）放在临时目录，核验完即清理，不当作交付附件，也不留在个人数据目录里，以免混入用户文件或被提交进 git。
- 新建或重新排版默认用[墨蓝商务样式](resume-style.md)；用户指定样式或要求保留原格式时优先遵守。
- 文件名为 `resumes/<主名>-v<N>.<扩展名>`，主名有三种：`通用版`；同方向海投的方向版 `<方向>方向`，例如 `数据分析方向-v1.pdf`；JD 定制版 `<公司>-<岗位>`。源稿、PDF、DOCX 同版本同主名；只为有变化的版本递增 N，已交付的文件和同版源稿保留。任务记录只指向检查完成的当前版本。
- 旧版的 `通用版.md`、`<公司>-<岗位>.md` 等历史文件不批量改名，也不为统一目录移动或打断旧链接；下次交付该岗位时按新名生成新版本。修改理由沿用已有记录，不每轮另写说明文档。

## 以实际成品核验

1. **PDF 以脚本结果为准。**退出码 0 即已核对：文件确为 PDF、页数不超上限、没有残留占位符、文字可提取而不是整页图片、文字层没有部首替代字符（出现时脚本自动换字体重试）、PDF 里每行文字都和源稿原样一致、先后不变（数字对调、改写、成果挪到别的经历下都查得出）。真实投递稿以 `--final` 通过为准，演练稿的最终版以 `--final --sample` 通过为准。
2. **看版面。**脚本不看版面长相。打开或渲染实际 PDF 的每一页，核对纸张、边距、有无裁切重叠，再按[实际排版检查](resume-style.md#实际排版检查)看样式细节；不能只确认文件生成或标题变成蓝色。
3. **看内容撑不撑得起。**按[逐条自查](resume-builder.md#逐条自查)判断，不以页面写满为准。完整稿明显不满一页（例如不足四分之三，脚本会对单页稿提醒），或主要经历多数条目缺东西时，不当作完成，回到[材料撑不起这个标准时](resume-builder.md#材料撑不起这个标准时)处理；不靠调大字号、加空行或灌水填满。只交 Markdown 或聊天文字时看不到版面，按条目检查，并说明没有检查实际版面。
4. **DOCX** 确认文件格式，实际渲染检查字体、换行和分页，提取正文与源稿逐段比对数字、日期、姓名、岗位和贡献边界，忽略合理空白和项目符号差异，不忽略事实变化。用常见可用字体；系统缺少思源黑体或微软雅黑时，用 Arial Unicode MS 等本机中文字体并在交付说明里注明。
5. **没法跑脚本时**，在第 2、3 步之外至少确认文件类型和页数，并用能按 ToUnicode 解析中文字体的工具提取文字与源稿比对（直接读原始字节会把正常正文显示成乱码）；出现错字或部首替代就换字体重新导出。确认文字可选择、不是整页图片，条件允许时检查字体嵌入。
6. 发现缺字、漏段或分页问题就修复并复查。宿主只能生成其中一种格式时，先交实际通过检查的文件和可编辑源稿，说明另一格式缺什么能力；只有 Markdown 时如实交 Markdown。未检查的格式不称为验证通过。

## 对用户怎么交付

只有源稿或部分格式可用时说明实际状态，不链接不存在或尚未检查的文件；材料入口里当前文件与历史版怎么放见[材料入口模板](../assets/materials-template.md)。

聊天先给当前阶段已核验文件的可打开链接，再简述主要修改和一个必要待办。默认不把通用版、历史版、源稿、QA 文件一起当附件列出；材料多时附材料入口，用户明确要源稿或全部版本时照给。文件必须实际存在、可打开，不能只贴文件名。检查明细留在记录里，聊天只简要说明已检查分页和文字；没有待办就结束。
